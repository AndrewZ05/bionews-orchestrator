Overview

The orchestrator is a plugin-based ETL system: each data source has an extractor plugin and a YAML config, and data flows Extract → Parquet → GCS → BigQuery staging → hash-merge → production → post-process SQL. Every run is tracked centrally in BigQuery so it can be alerted on and monitored.

There are five independent alerting mechanisms. The first three are the day-to-day signal; the last two are operational safety nets.

#MechanismAnswers the question
1Job failure alerts"Did a pipeline run fail or complete with warnings?"
2Freshness audit"Is any production table stale (not updated recently enough)?"
3Anomaly audit"Did a table's data pattern look wrong (missing dates, bad volume, schema/quality drift)?"
4Git drift monitor"Is a deployed checkout running stale code because git pull is stuck?"
5Orphaned job cleanup"Is a job stuck in RUNNING even though its process is dead?"

All notifications are email over SMTP (Gmail). Everything is recorded in the orchestrator_monitoring, freshness_audit, and anomaly_audit BigQuery datasets.

How a job runs (the process)

Understanding the job lifecycle makes the alerts below make sense.

  1. Registration. When orchestrate.py starts a source, it writes a row to orchestrator_monitoring.jobs with status RUNNING, recording host, PID, user, command line, trigger, and timestamps.
  2. Locking. The job acquires a distributed lock in orchestrator_monitoring.job_locks (see shared/job_lock_bq.py). The lock is a lease that a background heartbeat refreshes every ~120s (ORCHESTRATOR_LOCK_HEARTBEAT_SECONDS). Only one run per source can hold the lock at a time. If the process dies, the lease stops being refreshed and expires within minutes — this is the authoritative "is it really running?" signal.
  3. Execution. The extractor runs. Per-table progress is recorded in orchestrator_monitoring.table_processing (rows inserted/updated, per-table status, staging errors).
  4. Completion. The job row is updated to a terminal status — COMPLETED, FAILED, or a partial/warning state — with completed_at, duration_seconds, and any error_message. The lock is released.
  5. On failure/warning → alert. A job failure alert email is dispatched (see Alert type 1).
  6. Independently, on a schedule, the freshness and anomaly audits scan production tables and email summaries; the git drift monitor checks the deployed code; and orphaned job cleanup reconciles any RUNNING rows whose process is actually gone.

Key idea: the job's status (in jobs) and its liveness (in job_locks) are tracked separately. A row can say RUNNING while the process is long dead — which is exactly what orphaned-job cleanup and the dashboard's lock column exist to catch.

Alert type 1 — Job failure alerts

Purpose: notify operators the moment a pipeline run fails or finishes with warnings, and hand them everything needed to diagnose and retry.

  • Code: shared/monitoring.py — send_job_failure_alert(job_id, source, error_message, config, severity="FAILURE") (an optional send_job_success_alert exists but is off by default).
  • Triggered from: orchestrate.py, on job failure / partial failure (and on success only if alerting.on_success is enabled).

Severity levels

Severity drives the subject prefix and email header. Defined in _SEVERITY_LABELS (shared/monitoring.py):

SeveritySubject tagMeaning
FAILURE[FAILED]The run failed.
PARTIAL[PARTIAL FAILURE]Some tables succeeded, some failed.
WARNING[WARNING]Completed, but with warnings.
INFO[INFO]Informational notice; completed.

Subject format: [SOURCE] [SEVERITY] <summary> — e.g. [FACEBOOK] [FAILED] Pipeline Failed.

What the email contains

  1. Severity-driven header.
  2. Job details — job ID, source, timestamps.
  3. The error message / status detail.
  4. Per-table tracking (from orchestrator_monitoring.table_processing): each table's status, rows inserted/updated, staging rows, and error text.
  5. Full log content pulled from the job's log_file_path (GCS or local).
  6. Auto-generated recovery commands — ready-to-run retry commands (same parameters, per-table retries, manifest-based retry, or a full rebuild for schema errors).
  7. References — the BigQuery table paths to investigate manually.

Alert type 2 — Freshness audit

Purpose: a scheduled scan that answers "is every important table as up-to-date as it should be?" by comparing each table's most-recent data date against configured thresholds.

  • Code: shared/freshness_audit/ — audit_runner.py (run_audit), email_sender.py (send_summary_email), status_rules.py (determine_status), yaml_target_loader.py (targets).
  • Results table: freshness_audit.table_freshness_results (one row per table per run); run metadata in freshness_audit.audit_runs.

Status values and how they're decided

StatusMeaning
PASSFresh enough.
WARNINGWithin the warning window (aging).
FAILPast the freshness threshold (stale).
ERRORThe table could not be validated/queried.
STATICIntentionally-unchanged reference data (not treated as stale).

Decision order in determine_status(days_behind, warning_threshold_days, freshness_threshold_days, is_static):

  1. days_behind > freshness_threshold_days → FAIL
  2. is_static and within threshold → STATIC
  3. days_behind >= warning_threshold_days → WARNING
  4. otherwise → PASS

Global defaults live in configs/table_freshness.yaml (e.g. freshness_threshold_days, warning_threshold_days, recipients, retry policy). Per-table overrides live in each source's YAML under an audit: block:

Email

Subject (date-stamped, ASCII): reflects run-over-run change — e.g. Table Freshness Audit Results - N NEW FAILURES, M recovered - YYYY-MM-DD, or ... - FAILURES FOUND - ..., or just ... - YYYY-MM-DD when clear.

Body: run ID + timestamp; summary counts (PASS/WARNING/FAIL/ERROR/STATIC); a "changes since last run" section (newly-failed and recovered tables); a BigQuery console link; a fixed-width table grouped by dataset (STATUS, DATASET.TABLE, LAST_DATE, DAYS_BEHIND, TOTAL_ROWS, RECENT_ROWS, POLICY); policy notes; and an ERROR-detail section.

Send decision: an email is sent only if any result is WARNING/FAIL/ERROR, or always_send is set. An all-clear run sends nothing (unless forced).

Alert type 3 — Anomaly audit

Purpose: a scheduled scan for tables whose data pattern looks wrong even if the table isn't strictly stale.

  • Code: shared/anomaly_audit/ — anomaly_runner.py (run_anomaly_audit), email_sender.py (send_anomaly_summary), and per-signal detectors. Targets come from the same loader as the freshness audit, so the two audits cover an identical table list.
  • Results table: anomaly_audit.anomaly_results; run metadata in anomaly_audit.audit_runs.

Detectors

DetectorDetectsSeverity
RecencyLatest expected dates are missing (lag beyond grace)HIGH
VolumeDaily row count is a statistical outlier (MAD-based band)MEDIUM
StructuralColumns added/removed mid-streamMEDIUM
Schema driftA column's type changed incompatiblyHIGH
QualityA metric column is entirely NULL/0HIGH

Each finding has a severity (HIGH/MEDIUM/LOW) and a scope: ACTIVE (current, actionable, emailed) or HISTORICAL (past, tracked in BigQuery, summarized as a one-line count only).

Configuration

Global tuning in configs/anomaly_audit.yaml (e.g. K = MAD multiplier, rel_floor, min_count, grace, history_days, min_history_settled), with optional per-table overrides:.

Email

Subject: Anomaly Audit Results - ANOMALIES FOUND - YYYY-MM-DD when there are active findings, else Anomaly Audit Results - YYYY-MM-DD.

Body: run ID + timestamp; totals by severity, by detector, and by dataset; "changes since last run" (new vs. resolved active anomalies); best-effort pipeline-job context; and a full findings table (SEVERITY, SCOPE, DATASET.TABLE, DETECTOR, DATE, OBSERVED, DETAIL, POLICY), color-coded, with historical rows dimmed.

Send decision: email is sent if there is ≥1 ACTIVE finding, or new historical outliers appeared, or always_send is set.

Mutual watchdog

Each audit checks whether its sibling has run recently: check_sibling_run(..., max_age_hours=36) queries the other audit's audit_runs. If the sibling has been silent > 36h, a warning is injected into the email body. This is best-effort — a failed check never fails the audit — and it's how a silently dead audit gets noticed.

Alert type 4 — Git drift monitor

Purpose: a deployed checkout that lags the remote runs stale code. This monitor catches a stuck git pull before it silently starves the pipeline.

  • Code: scripts/check_git_drift.py — evaluate_drift(repo, branch, remote) computes the drift; main() decides; _alert(title, message) emails via the configs/defaults.yaml notification block.

Alert conditions — an email is sent if any of:

  1. behind > --max-behind (default threshold 1 commit), or
  2. the working tree has uncommitted tracked changes (dirty) — this blocks git pull --ff-only, or
  3. the git evaluation itself failed (can't fetch/status).

Exit codes: 0 = OK, 2 = alert sent, 1 = error. The email includes the local vs. origin/main HEADs, the behind/ahead counts, the dirty flag, and the exact fix (resolve tracked changes, then git pull --ff-only).

Why this matters: a generated tracked file once dirtied the production VM tree, froze git pull for days, and starved the Identity Hub. This monitor exists so that never recurs silently.

Alert type 5 — Orphaned job cleanup (KILLED)

Purpose: reconcile the jobs table with reality — mark RUNNING rows as KILLED when the process behind them is actually dead. This does not send email; it corrects status (and is what the dashboard's Reconcile button and lock column surface).

  • Code: shared/job_manager.py — cleanup_orphaned_jobs(bq_client, dataset, hostname=None, stale_running_hours=None), with _cleanup_locked_orphans(...) for the lock-based pass and is_process_running(pid, os_type) for the local check.
  • Invoked from: orchestrate.py at startup, and on demand from the dashboard.

The four detection passes

  1. Lock-based (all hosts, OS-independent) — the authoritative pass. A RUNNING row whose source has no unexpired lock in job_locks is KILLED. Because the lock lease auto-expires within minutes of a process dying, an absent lock proves the job is gone regardless of which host or OS ran it. A grace window (default 120s, ORCHESTRATOR_LOCK_ORPHAN_GRACE_SECONDS) exempts a job that has inserted its RUNNING row but not yet acquired its lock.
  2. Process-based (local host only). RUNNING rows on this hostname (or with NULL hostname) are KILLED if process_id is NULL or the PID is not alive locally.
  3. Time-based (all hosts). RUNNING rows older than stale_running_hours (default 24h, ORCHESTRATOR_STALE_RUNNING_HOURS; set 0 to disable, max 336h) are KILLED. This is the eventual backstop for hosts/PIDs the local check can't see.
  4. Legacy _pipeline_executions. Rows stuck RUNNING for 120+ minutes in the pre-centralized table are KILLED.

The error_message on a killed row records which pass caught it (e.g. Process no longer running (auto-detected) or Marked KILLED: RUNNING for more than N hours ...).

Reconcile (recover stuck jobs)

Reconcile applies the same cleanup_orphaned_jobs rules described in Alert type 5: any RUNNING row with no live lock/process (host- and OS-independent) is flipped to KILLED.

  • Auto-reconcile: runs once per environment on first load — so simply opening the dashboard corrects bogus RUNNING rows.
  • Manual: the Reconcile button in the sidebar re-runs it on demand and reports how many jobs were killed. A Refresh button re-queries without reconciling; a "last updated" caption shows recency.

Status editing

Each row's status dropdown lets an operator override status directly (calls update_job_status). Allowed values (JOB_STATUSES): QUEUED, RUNNING, COMPLETED, FAILED, WARNING, CANCELLED, KILLED, REVIEWED. There is no state-machine enforcement — any transition is permitted, so use with care in PROD.

Log viewing

The Log button opens a modal that fetches the job's log_file_path via fetch_log_content — from GCS (gs://…) or the local filesystem — and renders it in a scrollable dark viewer. Missing files return a clear "not found" message rather than an error.

Filtering & caching

Sidebar filters (in a collapsible section): Source, Status, Hostname, User, Triggered By, Refresh Mode, a free-text Search (across job ID, error, command, job name, error type), Days back (1–90, default 14), and Max rows (50–5000, default 500). Jobs are cached 120s and locks 30s; Refresh/Reconcile/status-change all clear the caches.

Caveats & known limitations

  • Scheduling lives outside the repo. Cadence is defined in cron / Cloud Scheduler on the host; confirm it there.
  • Audits only email when there's something to say. An all-clear freshness or anomaly run sends no email unless always_send is set — so "no email" means "nothing actionable," not "the audit didn't run." The mutual watchdog (36h) is what catches a silently dead audit.
  • Freshness and anomaly audits share one target list, so they can't drift out of sync on which tables they cover.
  • Dashboard status editing is unguarded — any status→any status. Be deliberate in PROD.
  • Lock-based cleanup depends on a healthy job_locks table. If locks are unavailable, the dashboard shows orange "unknown" rather than falsely killing jobs, and the 24h time-based pass remains the eventual backstop.
  • Some email bodies reference the project bi-data-391216 explicitly. If you run under a different GCP_PROJECT_ID, verify the console links in emails point where you expect.
  • Email requires a Gmail App Password, not the account password.
